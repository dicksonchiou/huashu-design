# 產品UI展示動畫 Playbook

> **這是「宣傳的產品有UI介面」時的單一入口。** 商單、釋出動畫、功能演示，只要畫面主角是一個介面，先讀這份檔案再動手。
>
> 核心主張一句話：**產品動畫的質感最大來源是「真實UI + 電影運鏡」，不是特效。** 科技感靠讓觀眾認出「這就是那個產品」，靠鏡頭怎麼看它，而不是靠粒子、輝光、賽博漸變。一張真實截圖配一次克制的推近，勝過十層手搓的假介面。
>
> 參數出處標註約定：（shotcraft·卡名）= video-shotcraft 鏡頭卡實測值；（huarec）= 花錄 Studio 運鏡導演系統；（best-practices §x）（gsap-recipes §x）= 本 skill 既有 reference。30fps 語境，1f ≈ 33ms。
>
> 分工：本檔案管「UI 這個主角怎麼演」；鏡頭詞彙與運鏡動機見 `camera-language.md`；元素級運動語法（easing、stagger、FLIP、Chunk Reveal）見 `animation-best-practices.md`，本文只引用不復寫。

## §0 兩條公理（凌駕於八式所有參數）

| 公理 | 內容 | 出處 |
|---|---|---|
| **可見性不變數** | 任意時刻，游標與正在發生的 UI 操作必須在可視區內（含 8% 安全邊距）。違反的鏡頭寧可降倍率、並鏡或不拍 | huarec A1 |
| **視覺語言從產品生長** | 先提取產品自己的設計 tokens（字型/圓角/色板/柵格），全片只准複用或克制擴充。鏡頭卡只繼承運動語法和節奏，皮膚按目標產品重蒙 | shotcraft 公理 1 |

## §1 決策樹：真實UI截圖運鏡 vs HTML重建UI

這是本檔案裡**最影響工作量的一個決策**，兩條路差一個量級。預設從最省的路徑開始判斷：

```
產品UI要出場
 │
 ├─ 介面只需要「被看」（推近/巡覽/懸浮/對比）？
 │   └─ 是 → 【路徑一】截圖裝frame + 2.5D運鏡。到此為止，別重建
 │
 ├─ 只有少數幾個元素需要單獨動（一張卡浮起、一行資料滾動）？
 │   └─ 是 → 【路徑三】混合：截圖當底 + 關鍵元素切片重建
 │
 └─ 介面本身是敘事主體，元素要逐個登場/回應操作/改狀態？
     └─ 是 → 【路徑二】HTML重建。走 build-up 八式②
```

| 路徑 | 做法 | 工作量 | 適用判據 |
|---|---|---|---|
| 一 · 截圖運鏡 | 真實截圖放進 `browser_window.jsx` / `macos_window.jsx` 裝置框，容器上做 zoom/rotate/pan | 小時級 | 介面是「被觀看的物件」；觀眾不需要看到介面內部產生變化 |
| 二 · HTML重建 | 按截圖逐畫素重建可動的 DOM 結構 | 天級 | 元素需要獨立時間軸：逐步生成、typing、狀態切換、hover 回應 |
| 三 · 混合 | 全頁截圖當底層紋理，要動的元素摳成透明底切片疊在原座標上動 | 半天級 | 90% 畫面靜態、10% 元素要活。**多數商單的正確答案** |

**混合策略的關鍵**：切片元素動完必須歸位到截圖上的真實槽位。目標卡若懸浮在網格上方不落回佈局，觀眾立刻讀出「假」（shotcraft·type-and-filter，Q9 判例曾因此近乎整檔案重寫）。

混合路徑的五步操作：

1. 全頁 2x 截圖鋪底，裝進裝置框（網頁產品用 `browser_window.jsx`，桌面 App 用 `macos_window.jsx`）
2. 要動的元素按 layout.json 座標摳成透明底切片
3. 截圖底層在切片原位鋪「頁面底色補丁」蓋掉烤入的原元素（spotlight-hero-card 的原位補丁手法：卡起飛後原位鋪底色補丁 + 強調色呼吸描邊，落地瞬間增亮消失）
4. 切片疊在補丁上做動畫，終點回到 layout.json 槽位
5. 特寫推進段用 4x 高畫質切片 6f 交叉淡入蓋住低倍紋理（shotcraft·PageCam 配套技法）

**裝置框選擇**：框是「這是真軟體」的語境訊號，裸截圖懸在畫布上像貼圖。但框也吃掉畫面面積，特寫推進到 zoom 2x 以上時框已出畫，此時可直接用無框切片。

### 素材三件套（走路徑一/三之前先採齊）

shotcraft pipeline 階段 1 的標準採集物（shotcraft·六階段 pipeline）：

| 素材 | 規格 | 用途 |
|---|---|---|
| 全頁 2x 截圖 | 裝置畫素比 2 起，長頁整頁截 | 底層紋理；推近後不糊的下限 |
| 元素透明底切片 | 要單獨動的元素逐個摳出，4x 更佳 | 混合路徑的「演員」；特寫推進期 6f 交叉淡入蓋住低倍紋理 |
| layout.json 座標表 | 每個切片在全頁座標系裡的 `{x,y,w,h}` | 動完歸位的「真實槽位」依據；標註/高亮框的定位錨 |

截圖來源走 `brand-asset-protocol.md` 的 UI 截圖採集協議（App Store 截圖、官網 screenshots、演示影片截幀、使用者帳號實截），品質門檻同樣適用「5-10-2-8」。推近特寫下文字發糊的根治辦法（CSS `zoom` 佈局級縮放替代 transform scale）見 `camera-language.md`。

## §3 八式詳解

### ① 3D展示臺 / hero特寫

把一個核心物件（卡片/面板/模組）立成產品的原子單位。質感最高、節奏最慢的一鏡，適合放在開場後的「單主角立傳」段。

| 參數 | 典型值 | 調節手感 |
|---|---|---|
| 相機機位 | rotY 34° 主導 + rotX 僅 8°，perspective 1200px | 側拍優於俯拍，「從左側拍攝而不是從下方」；rotX 一大就變成看桌面 |
| 推進 | 全頁 zoom 0.78 靜止一拍，再 16f 推進到 zoom 2.6 | 推進前的靜止是「讓觀眾先看到全域性」；直接開推沒有空間感 |
| 動作弧 | rise 10f（`cubic-bezier(0.2,1.25,0.3,1)` 過沖）→ 懸停 54f（sin bob 振幅 4px 週期 40f，translateZ 110px）→ reseat 18f 落地 press scale 0.997 | 鎖定到落地約 3.3s，質感鏡頭就要慢到這個量級；初版幾乎總是偏快 |
| 輪廓光束 | SVG rounded-rect 描邊跑兩圈：第一圈 14f 快而亮，第二圈 20f 慢而弱（opacity 0.62） | 兩圈快慢有別才讀作「持續掃描」，一圈是眨眼；光束全片只給主角一次 |
| 雙層影 | `0 8·lift px …, 0 46·lift px 90·lift px` 隨懸浮高度生長 | 影子不隨高度長，懸浮就不成立 |
| 聚光燈引導 | 遊走光經 4 箇中間站鎖定卡心，光池半徑 620→420→360 收攏，鎖定瞬間 +6% 脈衝；外部 vignette 0.16→0.42 壓暗 | 中間站讓「隨機照射」可信，直奔目標讀作程式化；vignette 是聚光燈的另一半 |
| 懸空註記（可選） | 卡側浮現兩行襯線註記，translateZ 92px + bob 週期 44f（與卡 40f 相近但不同步） | 「共感」而非映象同步；註記必須活在同一 3D 空間同一臺相機透視，平面疊字會破壞空間統一 |

（以上全部 shotcraft·spotlight-hero-card 實測值）

已知坑：收尾禁「zoom 2.6→2.58」一類尾漂，呼吸必須是真靜止；開場多卡群舞撐不起第一印象，直接從單主角+完整動作弧起稿；逐卡 glint 被判例兩次否決，光效嚴格只給主角。

搭配運鏡：dolly-in 推近 + 鎖定後靜止 hold（見 `camera-language.md`）。倍率跨度大於 2x 時長按對數伸縮，禁彈簧過沖（huarec）。

### ② 介面逐步生成 build-up

介面「從無到有」的登場敘事。**build 順序有語法**：chrome（視窗框/標題欄）→ 骨架（灰條佔位）→ 內容塊 stagger → 資料（數字/圖表最後活）。觀眾對 skeleton screen 有免費預期，灰條一出現就知道內容要來。

三張來源卡按物件分工：**一個介面**逐級變真用 skeleton-reveal；**一組行/卡片**嵌入列表用 row-embed；**一份文件**被寫出來用 document-typewriter-reveal。

| 參數 | 典型值 | 調節手感 |
|---|---|---|
| 三級顯影 | 塗鴉（每 5f 換種子「煮沸」）→ 換真一拍 8f 加速縮退 + 骨架 spring 彈入 → 骨架行錯峰 6f 滾入 → 顯影行錯峰 13f、行內 12f | 換真一拍必須快而果斷，拖長成 crossfade「躍遷」就沒了；三級佈局必須嚴格同構，錯位讀作換了個頁面 |
| 逐詞進場 | 2.5f/詞 上浮 14px；末行末詞 +14f 晚半拍 | 晚半拍是「載入完成」的句號；全部齊落平淡 |
| 行嵌入 | 第 i 行 cue = 12 + i·9，飛行 12f；`perspective(900px) translateY(−120·air) rotateX(16°·air)` | **rotateX 收平是「嵌入」的關鍵讀感**，純 translateY 只是「落下」 |
| 嵌入強調縫 | 底邊 2px 強調色縫從中心 5f 展開、8f 淡出 | 給每次嵌入一個確認點，但要淡得快 |
| 文件逐塊 | 第 g 塊 cue = 6 + g·3.5，每塊 wipe 8f；強調色 caret 只跟最新塊 | **「塊數×節拍先對預算」是核心算術**，塊多了先砍塊不加速；「永遠只有一個筆尖」，兩個 caret 同時閃就是兩個作者 |

（skeleton-reveal / row-embed / document-typewriter-reveal 三卡實測值）

已知坑：真內容層貼產品截圖時，骨架灰條行高與槽位要按截圖量，別按想象排；塗鴉級別不畫細節，太像 UI 第一級和第二級就沒差了；mock 文案不出現客戶/成員真名。

搭配運鏡：顯影段配 1→1.34 緩推（給「湊近看清」的視線動機）；build 全程別加鏡頭橫移，介面在變的時候鏡頭要穩（huarec：全螢幕級變化不推）。

### ③ 使用者 typing 模擬

模擬真人在輸入框/終端打字。與已有的 **Chunk Reveal（AI 流式輸出）是兩回事**：AI 輸出是不規律 chunk 湧現（best-practices §4.5、gsap-recipes §3.4，那套繼續用，不在這裡複寫）；使用者輸入是逐字元、勻穩、帶猶豫的人手節奏。寫錯場景是高頻事故：把使用者打字做成 chunk 會讀作「輸入框自己在生成」。

| 參數 | 典型值 | 調節手感 |
|---|---|---|
| 打字速度 | 正文 3f/字元；終端 2f/字元；裝飾性小字 0.7f/字元 | 「初版嫌快重工後的定稿值」；互動演示按真人操作速度，這是判例級鐵律 |
| 游標狀態機 | 打字時**常亮**，打完轉 8f 週期閃爍 | 打字中閃爍讀作卡頓；常亮→閃爍的切換本身就是「打完了」的訊號 |
| 退格修正 | 偶發一次：多打 1-2 字元，停 4-6f，退格，再打對 | 「人會打錯」是最便宜的真實感；但必須預寫進指令碼（幀確定性），不是執行時隨機 |
| 確認停頓 | 打完到頁面回應留 11f（0.37s）呼吸 | 打完立刻回應讀作機器自動，觀眾跟不上因果 |
| 程式碼打字 | 終端 2f/字元；語法高亮隨打字漸進上色（目前 token 打完即著色），不是打完整段再統一變色 | 統一變色是「貼上」不是「寫程式碼」；高亮延遲半個 token 內觀眾無感 |
| 截圖上打字 | 底色補丁蓋掉截圖裡烤入的 placeholder（保留圖示），文字層疊上去打 | 直接疊字會和烤入的 placeholder 重影 |

（shotcraft·type-and-filter 實測值）

退格修正的確定性寫法（預寫指令碼，不是執行時抽籤）：

```js
// 把「打錯→停→退→改」編譯成字元事件表，時間軸只是回放
const script = typeScript("nano-lab", {
  perChar: 3 / 30,                       // 3f/字元
  typo: { at: 5, wrong: "0", pauseF: 5 } // 第5字元處打錯一個"0"，停5f再退
});
// script = [{t:0, text:"n"}, {t:0.1, text:"na"}, ... {t, text:"nano-0"},
//           {t+0.17, text:"nano-"}, {t+0.27, text:"nano-l"}, ...]
// 渲染層按 t 查表取 text，雙向 seek 安全
```

搭配運鏡：打字前相機先上移/推近到輸入框（先給鏡頭再動手，可見性公理）；打字期間鏡頭鎖死。

### ④ 游標操作敘事

游標是 UI 演示裡唯一的「人」。元件用 `assets/cursor.jsx`（CursorSprite / ClickRipple / hover 聯動 hook，兩種時鐘驅動，API 見該檔案頭註釋）。

軌跡演算法不在此複寫：貝塞爾弧線 + 收斂手抖見 best-practices §3.5，GSAP proxy 寫法見 gsap-recipes §3.5。本式補齊的是**點選與聯動的參數**：

| 參數 | 典型值 | 調節手感 |
|---|---|---|
| 雙圈 ripple | 兩圈同心，**起點差 3f**，半徑 14→54 / 14→78px | 單圈太輕看不見；差 3f 是「一次點選的漣漪」，差多了像點了兩下 |
| 擴散/消散解耦 | 擴散 out-cubic 22f，消散線性 26f | 擴散要衝、消散要勻；同一條曲線管兩件事會「閃一下就沒」。緊湊場景可壓到各 10f（type-and-filter 用的就是壓縮版） |
| 點選預備 | 游標 scale 0.85（power1.in 約 3f）→ back.out 回彈 | Anticipation 讓點選有「按下去」的重量（gsap-recipes §3.5 同款） |
| hover 聯動 | 游標進入目標區，目標同幀亮起（brightness +6% 或 hairline 描邊浮現），游標離開即撤 | 目標不回應，游標就只是貼圖；聯動視窗按軌跡進度宣告，不做執行時命中偵測 |
| 游標角色分工 | 操作游標（點選有 payload）vs 表演游標（位移即劇情，具名協作游標雙人舞/群演） | 游標要點東西時用本式；純敘事的協作游標是另一場戲（shotcraft·collab-cursor-moves），同片可共存但別混 |

表演游標兩式速查（協作/多人主題時用，參數出自 collab-cursor-moves）：

| 式 | 機制 | 關鍵參數 |
|---|---|---|
| dialogue-duet 雙人舞 | 藍/綠兩枚具名游標靠近對話、上下分弧繞位交換（R≈270px）、名牌一亮一暗燈光交接、綠游標 easeIn 放大數十倍成轉場遮擋 | 全部三次貝塞爾位移，無 linear；兩枚同弧同向會有相撞感，上下分弧是「禮讓」 |
| cast-ensemble 群演 | 5 枚彩色游標 delay 0/5/9/13/17f 錯峰 spring 飛入，雙頻正弦漂移駐場（0.055/0.021 rad/f、幅度 ±46/30px），一枚打字 cameo | 名牌晚 12f 淡入才是「人到了自報家門」；聚攏後漂移衰減到 25% 保留，完全靜止的游標群讀作宕機 |

已知坑：游標移動全程必須遵守可見性公理，目標在畫面外就先動鏡頭再動游標；協作游標的名牌顏色=身分編碼，全片一致，中途換色觀眾以為換了人；漂移游標永遠不許蓋住正在閱讀的主內容。

搭配運鏡：點選確認後相機 16f 推進（zoom≈2.2）穿透進詳情頁，是「點選→進入」的標準交棒（type-and-filter）；轉場接法見 `camera-language.md`。

### ⑤ UI狀態轉場時間軸化

tab 切換、modal 彈出、頁面路由推入。**時間軸驅動的重放和可互動原型是兩種程式碼形態**，從原型改渲染稿時逐項翻譯：

| | 可互動原型 | 時間軸重放（渲染用） |
|---|---|---|
| 觸發 | `addEventListener('click')` | timeline 上的 label / position 參數 |
| 狀態切換 | `classList.add` + CSS transition | 顯式 tween（gsap-recipes §6.1 禁區規則） |
| 開啟/關閉 | `display: none` 切換 | `autoAlpha` tween |
| hover | `:hover` 偽類 | 按軌跡進度宣告的聯動視窗（八式④） |
| 隨機 | `Math.random()` | mulberry32 種子預生成（gsap-recipes §6.4） |

改稿後 `grep "addEventListener\|classList\|transition:"` 逐條清零。狀態必須是時間的純函式，preview 裡看著正常、渲染才穿幫的 bug 全部源於此。

| 參數 | 典型值 | 調節手感 |
|---|---|---|
| modal / 命令面板 | 背景 10f 壓暗至 rgba(20,20,20,0.45) + blur 10px；面板 −20px→過沖 +8px（9f）→落回（6f）；候選行錯峰 i·4f | 背景不壓暗，面板就沒有「浮在上面」；過沖量 8px 是「輕落」，再大變玩具 |
| tab 切換 | 指示條用 FLIP 滑移（best-practices §4.1），舊內容 5f 淡出下沉 8px，新內容 8f 淡入上浮 | 指示條和內容不同步是廉價感來源：條先走、內容跟半拍 |
| 路由推入 | 新頁從右側整頁推入 12-16f，舊頁同向退 30% 距離 + 變暗 | 舊頁退小距離（視差）比等距推讀感深；等距是「傳送帶」 |

（modal 參數為 shotcraft·command-palette-summon 實測值）

已知坑：狀態轉場是「一鏡一動效」的重災區，一次轉場裡 tab 又切、toast 又彈、資料又滾，觀眾什麼都沒看清；一鏡只演一次狀態變化。

搭配運鏡：狀態切換瞬間鏡頭必須靜止，切完再動（huarec 鏡間語法：變化是注意力消費，別和鏡頭運動疊加消費）。

### ⑥ 介面3D巡覽

展示一個長介面/多個畫面介面的「空間感」鏡頭。雙卡分工明確，選錯卡是這一式的主要事故：

| 卡 | 機制 | 適用 |
|---|---|---|
| steep-tilt-glide | **鏡頭靜、頁面動**：頁面斜置 rotateY −60°，自己勻速滑過畫面 | 頁面當「展品」列隊走過；內容不需要讀清，看的是體量和質感 |
| graze-face-tour | **鏡頭動、頁面靜**：頁面群懸浮定住，鏡頭貼臉遊覽 | 要在巡覽中看清區域性內容；鏡頭有「參觀者」人格 |

| 參數 | 典型值 | 調節手感 |
|---|---|---|
| 斜置角 | rotateY −60°，實戰裁決區 55-65° | −45° 被判「不夠斜」，>−70° 內容讀不清 |
| 懸浮高度 | 120-180px（graze-face-tour） | 低了貼地沒有「陳列」感，高了影子斷聯 |
| 群體錯峰 | 錯開起點但下落重疊並行 | 完全順序落是「排隊打卡」，重疊才是「一批到場」 |
| 段間銜接 | 交叉淡化 ≥8f | 硬切會黑閃；巡覽是連續空間，不許跳切 |

（shotcraft·steep-tilt-glide / graze-face-tour 實測值）

多頁同一個畫面陳列的第三變體（shotcraft·page-waterfall-wall）：3 列頁面瀑布牆，rotateX 20° + perspective 1000px，相鄰列 loop 週期差 ≥25%（如 12/9/14s）且中列反向。適合收場段「產品有很多頁面」的體量陳述，內容不需要讀清。週期差小於 25% 時三列會週期性對齊，「牆」瞬間變成「表格」。

已知坑：兩卡機制不可混用，頁面和鏡頭同時動，觀眾失去參照系（暈）；巡覽用的頁面紋理必須 2x 起，斜置放大後糊得最快。

搭配運鏡：這一式本身就是運鏡主角，前後鏡頭要靜（能量交替）；鏡頭路徑與 orbit 詞彙見 `camera-language.md`。

### ⑦ 長頁滾動敘事

長落地頁/文件/時間線的「快滾急剎」。滾動本身不是內容，**剎車點才是**。

| 參數 | 典型值 | 調節手感 |
|---|---|---|
| 剎車曲線 | `Easing.out(Easing.exp)` 一條曲線 50f 走完全程 | 分段減速會「泵」；一條 expo 曲線天然是「猛滾漸停」 |
| 運動模糊 | blur 由幀間位移差分驅動，速度大糊、停即銳 | 恆定 blur 是「鏡頭髒了」；只在動的瞬間有模糊，靜止幀永遠銳利（huarec 同款結論） |
| 目標行強調 | 停位後目標行 scale 1.03，其餘退暗 0.38 | 退暗別到 0，上下文要在；1.03 是「呼吸」不是「彈出」 |

（shotcraft·scroll-brake-moves 實測值）

多剎車點的預算管理（huarec 舒適預算，直接搬）：相鄰兩次「滾動+剎車」間隔 ≥2.6-3.0s；任意 15s 視窗內 ≤4-5 次；每個剎車點停留 ≥1.2s 再開滾。剎車點是注意力消費，比滾動本身貴。

已知坑：滾動期間禁推近，「滾動時推近會暈」（huarec：全螢幕級變化不推鏡頭）；剎車點沒有內容強調（目標行不抬升、其餘不退暗）時，觀眾不知道為什麼停在這。

搭配運鏡：急剎後可接一次輕推近（1.3x 檔）進目標行，但必須在完全停穩之後；檔位表見 `camera-language.md`。

### ⑧ feature callout 標註

在真實截圖上「指給觀眾看」。四個子配方，共同原則：**標註是導覽員，不是介面的一部分**，風格上要和產品 UI 拉開一層（襯線字/手寫感/強調色）。

| 子配方 | 參數 | 調節手感 |
|---|---|---|
| 標註線生長 | SVG 路徑 stroke-dashoffset 描線，12-18f，out-cubic；先線後字，字線上到達後 5f 淡入 | 線字同出讀作貼紙；線是「手指划過去」的時間 |
| 高亮框 | 目標區 rounded-rect 描邊 8f 展開 + 框外壓暗 0.3 | 只描邊不壓暗，視線不聚；壓暗超過 0.5 變審訊燈 |
| 放大鏡 | 圓形 loupe 內嵌 2-3x 高畫質切片（不是 CSS 放大截圖底），描邊 2px + 軟影，8f overshoot 彈出，跟隨目標 10-14f 緩移 | loupe 裡必須是高解析度切片，放大糊紋理等於自曝素材差；一鏡最多一個 loupe |
| 連線說明卡 | 說明卡浮在 3D 空間裡，translateZ 90px 量級 + bob 週期與主體相近但不同步 | 同一 3D 空間同一臺相機；平面疊字被判例否決（spotlight-hero-card 懸空註記同款約束） |
| before/after slider | 快甩 12f（out-cubic 8%→76% 過沖回彈到 70%）→ 停 18f → 慢掃 48f 到 40% 定格；速度比 5:1；after 層 clip-path 跟杆；手柄速度差分驅動 scaleX 微拉伸峰值 1.18 | 速度比 <3:1 節奏對比不可感；快甩宣告「變了」，慢掃證明「變在哪」；慢掃停 40% 讓 after 留在定格裡 |

（slider 為 shotcraft·before-after-slider-scrub 實測值）

已知坑：before/after 兩版必須同佈局同機位，否則讀作兩個頁面；before 用真實舊態（注入舊資料/關閉功能），不手搓「故意醜」的假 before；角標放內容區，別壓側欄頭像。

搭配運鏡：標註出現前鏡頭先推到 1.3-1.45x 檔讓目標區佔滿畫面（huarec：內容佔可視區 80%），標註期間鏡頭鎖死。

## §3.9 八式在全片能量骨架裡的落位

單式只是鏡頭，成片要按 promo-energy-arc 四段位排（shotcraft·導演層三件套；分鏡紀律「hold/rest 幀預算先撥出再排動效」同樣適用）：

| 能量段 | 時長佔比 | 放哪幾式 | 理由 |
|---|---|---|---|
| ① 品牌開場 | 8-12% | 不放 UI 式 | 字標 hold ≥1s，UI 別搶開場 |
| ② 單主角立傳 | 12-15% | ①hero特寫 或 ②build-up | 質感最高節奏最慢的一鏡，全片只有一個位置 |
| ③ 功能爬升 | 55-65% | ③④⑤⑦⑧ 交替，每鏡綁一個獨特功能 | 中高低能量交替；⑧callout 是低能量呼吸位的好填充 |
| ④ 釋出會收場 | 13-16% | ⑥3D巡覽（全家福變體） | 全片能量峰值，多個畫面同框陳列後 sign-off |

聲音鉤子速查（畫面鎖定後才做，釘幀寫相對錶達式，shotcraft 階段 5）：

| 式 | 釘什麼音 |
|---|---|
| ① hero特寫 | 彈起 whoosh-big、光束 sparkle、reseat 一聲 snap，三動作三專屬音 |
| ② build-up | 換真一拍 pop，逐行顯影各一聲極輕 tick，末詞晚半拍處輕 chime 收束 |
| ③ typing | keyboard 音與打欄位嚴格等長（按字元數截）；不足截、超長裁 |
| ④ 點選 | click 是全片最響的一聲（響度分層的頂），ripple 無聲 |
| ⑤ 狀態轉場 | modal 彈出一聲柔 pop，路由推入一聲 whoosh-fast |
| ⑥⑦ 巡覽/滾動 | 勻速段無聲或極輕 hum，急剎一聲悶 thud |
| ⑧ callout | 標註線生長配極輕 draw 摩擦音；slider 快甩 whoosh + 回彈 tick，慢掃無聲 |

## §4 節奏鐵律（從 shotcraft 判例繼承，UI 演示專用）

1. **互動演示按真人操作速度走。** 打字 3f/字元、點選前有移動、回應前有呼吸。互動鏡頭的第一版幾乎總是偏快，起稿就按人速（判例 R3，type-and-filter 因此重工）。
2. **批次動效收尾 0.5s 靜止。** 網格收斂完、列表嵌完、面板落完，滿板靜止半秒再走下一鏡。
3. **退場必須錯峰。** 非目標元素按閱讀序 0.4f 間隔錯峰淡出，「同時消失讀作頁面崩潰」，哪怕只差 0.4f 也夠（type-and-filter）。
4. **一鏡一動效。** 一個鏡頭只講一個 UI 行為；同一個畫面兩個動效在搶戲，觀眾兩個都沒看見。
5. **收尾真靜止。** 呼吸位、hold 幀裡禁任何尾漂（zoom 微變、opacity 微調都算）；「靜」是設計出來的一拍，不是沒排到動作。

## §5 與三方向門 / 資產協議的銜接

**三方向板怎麼出**：產品 UI 動畫的三方向不是三套視覺皮膚，而是**同一份 UI 素材的三種鏡頭敘事詮釋**。素材三件套採集一次，三個方向複用。例如同一張產品截圖：方向 A 走八式①（單主角 hero 特寫立傳）、方向 B 走八式②（build-up 從無到有講生成能力）、方向 C 走八式⑥+⑦（巡覽+滾動敘事講體量）。方向板各附 2-3 幀關鍵幀 thumbnail，讓花叔選的是「怎麼講這個介面」，不是「哪張圖好看」。三方向門是 100% 硬門，指定風格也不豁免（SKILL.md 既有規則）。

**UI 截圖取材走 `brand-asset-protocol.md`**：數位產品的 UI 截圖在該協議裡就是一等公民資產（識別度貢獻極高），採集管道、5-10-2-8 品質門檻、brand-spec.md 固化全部照走。本檔案的增量只有一條：採集時按 §1 的素材三件套規格執行（2x 全頁 + 透明底切片 + layout.json），一次採齊，運鏡和重建兩條路徑都夠用。

**禁手搓假 UI**：找不到真實截圖時按協議備援（向使用者索取實截 / 官方演示影片截幀），不用 mockup 生成器湊，不用 CSS 畫一個「像那麼回事」的介面。我們在表達的是這個產品，不是「一個產品」。

**例外只有一個**：走了路徑二 HTML 重建時，重建稿本身就是「以真實截圖為基準的復刻」，必須對照截圖逐區塊校（字型、圓角、間距、圖示都從截圖量），重建完成後與截圖並排截幀對比。重建出一個「大概像」的介面，比直接用截圖更傷，觀眾對自己天天用的產品介面誤差極敏感。

## §7 常見失敗模式速查

| 症狀 | 根因 | 回哪節 |
|---|---|---|
| 「科技感不夠」於是加粒子/輝光 | 方向就錯了，質感缺口在真實 UI 和運鏡 | 開篇主張 + §1 |
| 介面像貼圖懸在畫布上 | 沒裝裝置框、沒有影子語言 | §1 裝置框 + 八式①雙層影 |
| 推近後文字發糊 | 截圖倍率不足或柵格化解析度問題 | §1 三件套 + camera-language.md |
| 互動「像指令碼不像人」 | 打字/點選/回應全按機器速度跑 | 八式③④ + §4 鐵律 1 |
| preview 正常、渲染穿幫 | 事件驅動狀態混進了時間軸 | 八式⑤對照表 + gsap-recipes §6 |
| 觀眾說「有點暈」 | 鏡頭和頁面同時動，或剎車點超預算 | 八式⑥⑦ + huarec 預算 |
